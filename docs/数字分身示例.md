# 数字分身完整示例

首次使用可从[初始化引导](初始化引导.md)创建独立实例、运行离线配对与完整示例，再分步配置自己的应用和工程。下文保留底层准备、容器和宿主入口。

示例场景：同事通过飞书询问最近一次发布，分身调用本机合成工程，发现流量从 10% 调整到 100%，返回事实、示例规则判断与证据摘要。工程不依赖公司网络、私有仓库或个人登录。

下面保留内置发布检查示例。接入自己的工程请使用[本地工程接入](本地工程接入.md)：另有独立 Git 工程模板、可注册的多个能力和固定 JSON 入口，沿用同一飞书与模型链路。

## 默认离线体验

使用 Python 3.11+，不安装额外依赖。先完成仓库治理检查并提交代码，从干净的完整提交导出不可变示例。下列 `$Commit` 必须为实际完整 SHA，运行根选择源码目录之外的新目录：

```sh
Commit=$(git rev-parse HEAD)
python3 -B scripts/digital_twin.py prepare --instance examples/digital-twin/instance.example.json --runtime ../im-agent-example-runtime --commit "$Commit"
python3 -B ../im-agent-example-runtime/source/scripts/digital_twin.py smoke --runtime ../im-agent-example-runtime
python3 -B ../im-agent-example-runtime/source/scripts/digital_twin.py status --runtime ../im-agent-example-runtime
```

Windows 使用 `py -3.11`，先用 `$Commit = git rev-parse HEAD` 设置变量，并采用明确的源码外路径。后台常驻宿主应使用相同环境的 `pythonw.exe`，前台验收可使用 `python.exe`。

`prepare` 只导出固定 Git 提交，记录源码、工程文件哈希、依赖锁及实例配置，创建独立服务令牌，不启动任何服务。失败目录保留，不覆盖已有运行根。

`smoke` 在本机启动独立 worker 和宿主进程；经过真实 HTTP 的飞书 API 夹具完成回复和回读，随后验证重复输入和 transport 重建不会重复回复。各角色使用独立 SQLite。实际执行的工程入口为固定快照中的 `inspect_release.py`，请求只通过 stdin 传递，不拼接为命令。

结果写入运行根 `report.json`，`status` 只读账本计数，不启动或恢复进程。该验收范围是本机进程与 HTTP 夹具，真实飞书消息及模型调用均为零，不代表 Docker 或真实飞书已经实测。smoke 要求新的运行根；重复验收请准备另一个目录，不清空旧账本。

## 连接自己的独立飞书测试应用

使用企业自建测试应用，开启机器人能力与长连接事件订阅 `im.message.receive_v1`，授予官方接收私聊消息、发送/回复消息及读取消息所需权限。应用可用范围包含测试人。权限以开发者后台和官方 API 文档为准。先完成自己的测试应用发布/授权，再连接。

复制实例模板到源码外，修改以下字段：

- `profile` 改为 `feishu`。
- `identity.tenant`、`feishu.app_id`、`feishu.bot_open_id` 填自己的测试应用身份。
- 在 `feishu` 中增加 `accept_after_ms`，值为本次准备时的 Unix 毫秒时间戳（可用 `python3 -c 'import time; print(time.time_ns() // 1000000)'` 获取）。真实 profile 必须固定这个接收起点；此前的历史事件拒绝受理。重连沿用 manifest 中的原值，避免新账本执行应用积压的旧问题，也不丢弃本实例停机期间的新请求。
- `actors` 中填获准测试人的 `open_id` 和对应 `chat_id`，其他 identity 字段与实例一致。群聊还须明确 allowlist 成员，并在消息中 @ 该机器人。
- `owner` 仅标识分身归属；不会自动获得群权限或将 owner 的数据授权给其他人。
- `feishu.app_secret_env` 保持环境引用；秘密放在源码外的受保护环境文件或当前进程环境，不写入 JSON。

默认 `planner.provider=rules`：问候和帮助返回固定说明，其他文本触发同一个合成工程检查。它用于验证渠道与执行链路，不表示已经有完整开放域对话。

可选模型路由配置为 `{"provider":"deepseek","model":"deepseek-flash","api_key_env":"IM_AGENT_MODEL_API_KEY"}`。内置示例只在 `help` 与 `inspect-release` 中选择；独立工程则使用实例 `project.capabilities` 声明的能力及 `help`。模型不能改写发送者、原始问题、工程路径或返回的工程事实；仅在显式 Feishu profile 下启用。选择器显式关闭思考模式，使用 JSON 输出与 128 个输出 token 上限；请求携带能力名称与描述、人格和本条问题，不携带 actor 身份或业务凭据。模型失败会保留 unknown，不自动重复付费调用。离线测试不调用真实模型。

模型尝试在 `worker/planning.sqlite3` 的 `model_attempts` 中先持久记为 `started`；合法响应与已保存计划在同一事务变为 `verified`。回执只保存请求摘要、响应 ID 摘要、模型名、已核验能力和 token 用量，不保存密钥、提示词或思考内容。进程在调用期间退出，重建后标为 `unknown`，不会再次调用；已经保存的计划可以重试幂等入站。`status` 的 `worker/model_attempts` 可只读查看这些计数，HTTP worker 状态中的 `model_calls` 是保守的持久尝试数，包括尚未确定是否计费的 unknown；只有 verified 回执证明已收到有效模型结果，不能据尝试数推断账单。

用这份配置和固定 SHA 再 `prepare` 到另一个新目录。公共代码不提供任何现成应用身份，也不复用其他实例的生产应用、服务目录、队列、端口或凭据。

## 容器角色与本机执行器

准备完成后，运行根有独立 `compose.json`。它仅包含 transport 与 worker；host 在宿主执行。离线 profile 的 transport 自动装载合成事件与本机 HTTP 夹具，进程外联审计只允许回环和指定 worker；可以直接 `docker compose -f <运行根>/compose.json up --build -d`，再按下述方式启动宿主。CI 在 Linux 验证此路径，运行数据与凭据均为合成值。

真实测试应用 profile 可用自己的 Docker Compose 构建并启动：

```sh
docker compose --env-file /absolute/private/test-app.env -f /absolute/runtime/compose.json up --build -d
docker compose --env-file /absolute/private/test-app.env -f /absolute/runtime/compose.json port worker 8080
```

第一条命令需要替换为自己的绝对路径；环境文件包含配置引用的测试 App secret，可选模型 key 同理。镜像使用固定 Python 摘要和带完整 wheel 哈希的 `requirements-feishu.lock`；SDK 不进入宿主全局 Python。SDK 网络日志不回显授权 URL。

第二条命令返回专属 loopback 端口，采用这个地址启动宿主（示例中的端口须替换为实际返回值）：

```sh
python3 -B /absolute/runtime/source/scripts/digital_twin.py host --runtime /absolute/runtime --state /absolute/runtime/host --secrets /absolute/runtime/secrets/host.json --worker http://127.0.0.1:54321
```

收到提问后，transport 先持久受理再交给 worker；worker 路由后由 host 领取并执行；transport 只回复原问题，并通过官方读取接口核对消息内容、会话与应用发送者后确认回执。网络超时或回读失败时保留 unknown，不能靠重启或重新提问重发原任务。当前示例没有自动对账/人工重发 CLI。

Compose 的项目名、角色目录和 loopback 随机端口独立；不注册开机任务，不操作其他实例。运行根中的 manifest、令牌、账本、进程日志和报告均属于本地材料。宿主示例使用本次选定的标准库 Python；生产工程完整解释器/依赖冻结仍使用框架 bundle 机制及实例验收。

真实验收由获准测试人在飞书发送“检查示例项目最近一次发布”，核对只收到一条包含版本、流量变化、风险说明和证据摘要的回复。再核对运行根中的 worker 任务与 transport 回执。当前首次实现的代码验证与真实应用验收分别记录；没有真实验收记录时不宣称已通过。

验收结束后，前台宿主用 Ctrl+C 停止，再用相同环境文件移除本次示例的容器与网络；源码外运行根及账本保留：

```sh
docker compose --env-file /absolute/private/test-app.env -f /absolute/runtime/compose.json down
```

## 验证范围

| 验证方式 | 已核对的行为 | 范围 |
|---|---|---|
| 本机离线 smoke | 持久受理、宿主工程子进程、单条回复与 HTTP 回读、重复输入与 transport 重建 | 合成事件；零真实消息、零真实模型调用 |
| Windows/Linux CI | Python 3.11/3.13 行为回归与独立 Git 工程接入命令 | 合成工程与模拟模型响应 |
| Linux 容器联调 | transport / worker 容器和原生宿主经过合成 HTTP 夹具完成闭环 | 不连接真实应用或业务 |
| 独立应用验证 | 真实飞书提问、受限模型选择能力、宿主合成工程、单条回复和官方 API 回读 | 单条提问的能力路由；事实由本地程序产生 |

规则路由与真实模型路由均验证过合成发布检查结果，包含版本、流量变化、复核提示和证据摘要。模型仅选择已注册能力，框架保持原始问题、actor 和工程绑定；成功回执中保存模型与用量摘要，不保存密钥或思考内容。独立验证结束后停止测试角色并保留账本，具体运行身份、版本、消息凭据和开发记录保存在私有证据中。

自由生成业务答案、完整多轮协作、使用者自己的工程、Windows 真实收发和真实平台重投须分别验收。离线去重和重建测试不等于真实平台重投实测，通用示例通过也不代表某个私有实例已经发布或具有当前健康状态。
