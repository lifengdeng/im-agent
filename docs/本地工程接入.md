# 接入自己的本地工程

首次接入可先用[初始化引导](初始化引导.md)自动创建独立实例和桥接模板，再选择本工程的固定 Git 快照。下文说明桥接合同、执行边界及手工接线方式。

im-agent 负责飞书身份、受理、模型选择能力、工程调用与结果交付。你的工程负责实际工作、业务权限、事实来源和结果说明。工程可以保持私有，接入不要求公开工程源码，也不需要任何特定业务系统。

当前最小接入是一个独立 Git 工程和一个使用 Python 3.11+ 标准库的 JSON 桥接程序。每个示例实例连接一个工程，可注册 1–8 项能力。先用仓库自带的独立工程跑通，再替换桥接程序中的实现。

## 1. 建立独立工程并离线验收

从干净的 im-agent 检出运行；框架和工程分别提交、分别固定完整 SHA。Python 3.11+ 与 Git 即可完成此步，无需 Docker、飞书凭据或模型 key。首次检出先按 [README](../README.md) 安装仓库 hooks。

Mac / Linux，以下目标目录须尚不存在，命令在 im-agent 根目录运行：

```sh
mkdir ../my-local-project
cp examples/local-project/project/im_agent_project.py examples/local-project/project/project.json ../my-local-project/
git -C ../my-local-project init
git -C ../my-local-project add im_agent_project.py project.json
git -C ../my-local-project commit -m "Add local engineering capability"
cp examples/local-project/instance.example.json ../my-twin.instance.json

FrameworkCommit=$(git rev-parse HEAD)
ProjectCommit=$(git -C ../my-local-project rev-parse HEAD)
python3 -B scripts/digital_twin.py prepare --instance ../my-twin.instance.json --runtime ../my-twin-offline --commit "$FrameworkCommit" --project-repository ../my-local-project --project-commit "$ProjectCommit"
python3 -B ../my-twin-offline/source/scripts/digital_twin.py smoke --runtime ../my-twin-offline --question "检查我的工程当前版本和检查结果"
python3 -B ../my-twin-offline/source/scripts/digital_twin.py status --runtime ../my-twin-offline
```

Windows PowerShell，使用明确的 Python 3.11+：

```powershell
New-Item -ItemType Directory ../my-local-project
Copy-Item examples/local-project/project/im_agent_project.py, examples/local-project/project/project.json ../my-local-project/
git -C ../my-local-project init
git -C ../my-local-project add im_agent_project.py project.json
git -C ../my-local-project commit -m "Add local engineering capability"
Copy-Item examples/local-project/instance.example.json ../my-twin.instance.json

$FrameworkCommit = git rev-parse HEAD
$ProjectCommit = git -C ../my-local-project rev-parse HEAD
py -3.11 -B scripts/digital_twin.py prepare --instance ../my-twin.instance.json --runtime ../my-twin-offline --commit $FrameworkCommit --project-repository ../my-local-project --project-commit $ProjectCommit
py -3.11 -B ../my-twin-offline/source/scripts/digital_twin.py smoke --runtime ../my-twin-offline --question "检查我的工程当前版本和检查结果"
py -3.11 -B ../my-twin-offline/source/scripts/digital_twin.py status --runtime ../my-twin-offline
```

Git 提交使用你自己的已有身份；不需要推送或公开工程。若工程工作区正在修改，请先准备独立的干净检出，不隐藏或清除现有修改。接入源必须是仓库根目录，HEAD 与给定 SHA 相等、无未提交或未跟踪文件、无隐藏 tracked 文件及稀疏检出。

预期回复包含 `sample-notes`、版本 `1.0.0`、检查通过 `1/2`、需复核“文档链接”，并说明依据来自固定的 `project.json`，没有现场运行检查。运行根 `report.json` 应有 `passed=true`、`reply_count=1`、`readback_verified=true`；真实飞书消息与模型调用均为零。`status` 显示 `project=my-local-project`、实际工程 SHA 和成功账本计数。

规则路由在帮助之外总选择配置中的第一项能力，只用于离线验收。模型选择第二项能力的行为由模拟模型响应的自动化测试覆盖；真实模型接入见第 4 步。

## 2. 将桥接程序换成自己的能力

模板位于 [examples/local-project](../examples/local-project/instance.example.json)。保留根目录固定入口 `im_agent_project.py`，把实际实现放进自己的工程仓库；无需修改 im-agent 的 transport、planner 或 host 源码。

实例 JSON 中声明业务能力，路径与命令不属于配置或模型输出：

```json
{
  "project": {
    "id": "my-local-project",
    "adapter": "local-project-json-v1",
    "capabilities": [
      {"name": "inspect-status", "description": "查询本地工程当前版本、检查通过数量与需要复核的事项"},
      {"name": "list-checks", "description": "逐项列出本地工程的检查名称和检查状态"}
    ]
  }
}
```

这是完整实例中的 `project` 部分；其余字段使用模板。能力名须唯一，`help` 与 `request` 为保留名。模型从名称和描述选择；每个能力均使用实例中明确授权的完整 actor 列表，当前示例不提供逐能力的不同成员权限。需要更细权限时使用核心 Registry 的独立合同及私有 adapter。

host 启动固定解释器的隔离子进程，工作目录为工程快照，只从 stdin 传入一个 UTF-8 JSON：

```json
{"schema":1,"capability":"inspect-status","question":"检查我的工程当前版本和检查结果"}
```

模型只能返回 `{"capability":"inspect-status"}` 这样的提议。框架保留原始问题、actor、工程与快照绑定；没有模型提供的文件路径、Shell 或执行参数。桥接程序须再次核验 schema 和能力名，把问题当数据处理，不将自由文本拼接为命令、表达式或动态模块名。若工程本身使用 AI，仍须在工程内部约束其工具与业务权限。

程序成功退出时，stdout 只输出一个 JSON：

```json
{"text":"工程 sample-notes，版本 1.0.0。检查通过 1/2；需复核：文档链接。依据：固定快照中的 project.json。"}
```

`text` 为 1–7000 个字符，整个 stdout 不超过 32768 字节；不可增加 `actor`、`verified` 等字段。非零退出、超时（15 秒）或不合法输出不产生成功回复。框架包裹结果并固定 `evidence` 为工程文件清单的 SHA-256 摘要；`verified` 表示执行结果通过合同与绑定校验，业务事实的正确性仍由桥接程序保证。把版本、数据时间、依据和判断范围写进 `text`，不能用“执行成功”代替实际证据。

入口使用 `-I -B -X utf8`，不加载用户 site-packages 或 `PYTHONPATH`，不依赖相邻模块自动导入。仅传入少量系统临时目录变量和系统 PATH；飞书与模型 key 不传给工程，stderr 不进入聊天或公开报告。需要私密诊断时，由工程写入自己的受保护诊断位置，不能写回快照。

此入口运行的是操作人审阅过的可信本地程序，拥有宿主账号权限；它没有给任意第三方代码提供 OS 沙箱。当前便捷入口适合标准库桥接；含第三方 Python 包、Node、Codex、外部工具或业务登录的工程，需要自己的固定解释器、依赖 bundle 和私有 adapter，并按 [维护与发布规范](维护与发布.md) 验证。不要依赖开发中的 `.venv`、可变全局包或个人登录态来冒充已固定的运行依赖。

## 3. 理解快照和运行目录

```text
im-agent/                 通用框架 Git 检出
my-local-project/         你的工程 Git 检出，可保持私有
my-twin.instance.json     私有实例配置，只有环境变量名，没有密钥值
my-twin-offline/
  source/                 固定框架 SHA 的导出
  project/                固定工程 SHA 的导出，只在宿主使用
  manifest.json           两个 SHA、配置、源码/工程文件哈希与快照摘要
  compose.json            独立 worker / transport 容器与随机 loopback 端口
  secrets/                分角色的服务令牌
  worker/ transport/ host/ 各自账本和运行状态
```

运行根必须同时位于框架和工程源码之外，且为新目录。工程经 `git archive` 导出，入口及所有数据文件都进入哈希清单。链接、子模块、Git LFS 指针及受禁止的运行状态文件拒绝导出；含这些内容的工程先准备经过核验的独立发行仓库。凭据、聊天、数据库和未提交数据不应放进发行仓库，导出检查不能代替秘密与来源审查。

工程源码不会挂载给容器，也不在 Docker build context 中；容器仅拿到配置、注册描述和哈希清单。宿主每次执行前核验工程快照。编辑原工作区不会影响已准备实例；修改运行快照会拒绝执行。不要往快照写缓存或直接修补代码。

需要采用新的工程版本时，提交并核验新 SHA，准备新的隔离候选。此示例没有对现网同卷升级、历史合同迁移或自动版本跟随的发布 CLI；不能换一个空运行目录重接旧应用来绕过去重，也不能删除尚有请求引用的旧快照和账本。正式服务升级由实例维护流程处理。

## 4. 接入自己的飞书应用和模型

先完成前面离线验收。复制实例配置到新的源码外文件，沿用 `project`，设置自己的 `profile=feishu`、测试应用身份、完整 actor allowlist 和固定接收起点 `feishu.accept_after_ms`。身份对应关系、长连接、容器和宿主启动命令见 [数字分身完整示例](数字分身示例.md)。使用独立企业自建应用及自己的测试会话；仅有群 Webhook 的自定义机器人不能用于此接入。[飞书机器人说明](https://open.feishu.cn/document/client-docs/bot-v3/bot-overview)

私聊示例需要的应用权限如下；以当前开发者后台和官方接口要求为准，开通后须发布应用并使授权生效：

| 用途 | 权限 |
|---|---|
| 接收测试人的私聊事件 | `im:message.p2p_msg:readonly` |
| 以机器人身份回复 | `im:message:send_as_bot` |
| 读取原消息和最终回复以核验回执 | `im:message:readonly` |
| 可选：接收群内 @ 机器人 | `im:message.group_at_msg:readonly`，同时配置明确的群和成员 allowlist |

接收事件与回读是两个环节，只有接收权限不足以完成验收。依据：[接收消息](https://open.feishu.cn/document/server-docs/im-v1/message/events/receive)、[回复消息](https://open.feishu.cn/document/server-docs/im-v1/message/reply)、[获取指定消息](https://open.feishu.cn/document/server-docs/im-v1/message/get)。先验证私聊，再按需要验收群聊权限和范围。

使用该应用的官方 API 调试台及受控事件调试工具取得身份，禁止从其他应用复制 open_id：

| 实例字段 | 对应来源 |
|---|---|
| `feishu.app_id` | 本应用的凭证页 App ID |
| `feishu.bot_open_id` | [获取机器人信息](https://open.feishu.cn/document/client-docs/bot-v3/obtain-bot-info) 中的 `bot.open_id` |
| `identity.tenant` 及各 actor 的 `tenant` | 本应用接收事件的 `header.tenant_key` |
| actor 的 `user` | 本应用接收事件的 `event.sender.sender_id.open_id` |
| actor 的 `chat` | 同一事件的 `event.message.chat_id` |

仅做身份识别的调试接收器不执行工程、调用模型或发送回复；取得身份后先停止，再启动本示例。它不能与本示例或其他同应用接收端并行。`instance`、`agent` 是你选择的实例标识，在 identity 与 actors 中保持一致；`kind` 对应私聊 `private`。实际身份和原始事件留在私有目录。

在实例 JSON 中显式启用模型：

```json
{"planner":{"provider":"deepseek","model":"deepseek-flash","api_key_env":"IM_AGENT_MODEL_API_KEY"}}
```

模型名使用自己账号当前支持的 Chat Completions 模型。本示例实现官方 DeepSeek 接口，不提供任意 base URL 或多厂商配置。模型收到能力名称、描述、人格说明及本条问题；这些内容会发送给所选模型服务，填入前确认其适合该服务。身份、工程源码和宿主业务凭据不进入选择器请求。事实答案仍由本地工程生成。

源码外的受保护环境文件写入以下环境变量值，替换占位符；Mac/Linux 限制为本人读写，Windows 配置本人 ACL，不提交 Git：

```dotenv
IM_AGENT_TEST_APP_SECRET=REPLACE_ME
IM_AGENT_MODEL_API_KEY=REPLACE_ME
```

使用新配置和相同工程 SHA，重新执行第 1 步的 `prepare`，运行根改为新的源码外目录，例如 `../my-twin-live`；继续传入 `--project-repository` 和 `--project-commit`。再按 [容器角色与本机执行器](数字分身示例.md#容器角色与本机执行器) 的命令启动两个容器和宿主。前台验收可使用明确的 `python.exe`；Windows 后台宿主使用同环境 `pythonw.exe`。

## 5. 验收结果并停止测试

获准测试人私聊自己的应用发送“逐项列出工程检查”。模型应选择 `list-checks`，本地工程返回逐项结果；只收到一条回复，包含“文档链接：needs-review”及依据。也可询问“检查工程当前版本和检查结果”，应选择 `inspect-status`。每条新消息各产生一次模型选择；不要用新提问代替原任务的对账。

检查运行根的状态与账本，不只看聊天中的一句成功文案：

| 环节 | 验收证据 |
|---|---|
| 正确提问被受理 | `worker/planning.sqlite3` 的 intake，原始 actor 与问题保持不变 |
| 模型选择已注册能力 | `model_attempts` 为 `verified`，回执的 capability、模型名和用量可核对 |
| 宿主执行固定工程 | `host/executions.sqlite3` 的成功记录与工程 snapshot 对应 |
| 一条回复被回读核验 | `worker/worker.sqlite3` 任务 `delivered=1`，`transport/transport.sqlite3` outbox `verified` |

`digital_twin.py status --runtime <运行根>` 只读汇总这些状态。合成演示与模拟模型测试不代表你的飞书权限、模型账号、宿主平台或真实业务工程已验收。首次接入先做只读能力；业务写入的权限、幂等和对账由工程自己的合同负责。

模型、执行或投递为 `unknown` / `uncertain` 时保留现场并对账；重启不会自动重试未知业务或补发消息。示例没有人工重发、取消或完整多轮补问 CLI。验收后 Ctrl+C 停止前台宿主，再用启动时相同的 `--env-file` 和 `compose.json` 执行 `docker compose ... down`，保留账本、回执和快照。本示例不注册开机任务，不改变已有实例的框架绑定与生产进程。
